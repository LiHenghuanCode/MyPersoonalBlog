出发点

健康场景和一般问答的区别在于错一个数字的代价。所以整个系统的设计纪律只有一条： 不猜值——宁可拒绝并留痕，也不做静默修正。下面三块都是这条纪律在不同层面的展开。

一、OCR + VLM 多模态解析

问题

业务需求是患者上传检验或体检报告，来源有三类：电子 PDF、手机拍的照片、扫描件。系统要能解析这三类输入，而它们各有各的难点。

电子 PDF 的文字通常能准确提取，表格却未必能还原：有的表跨页后不再重复表头，有的用合并单元格表示「血常规」这样的类别，还有的根本没有画表格线。

照片和扫描件的问题出在识别环节。OCR 返回的是零散的文字块，块的顺序和表格的行列并不对应，「结果」列和「参考区间」列很容易错位，数值就对到了别的指标上。 后面的 LLM 会把错数总结得很通顺，最终报告里看不出任何问题。

处理方式

先按输入形态路由：电子 PDF 走表格结构还原；图片和扫描件同时走 OCR 和 VLM 两个通道，再按下面的规则合并两路结果。

  • 同名同值：交叉校验通过，合并成一条。
  • 同名异值：采信 VLM，因为它能看懂版面，知道数字属于哪一行哪一列。OCR 那条进入 rejected，原因记为「通道冲突采信 VLM」。
  • 只有 OCR 识别到：过一遍常识范围表，越界的进入 rejected。
  • 只有 VLM 识别到：同样过常识范围表。

合并后的结果做归一化和异常判定，再进入后续环节。之后按确定性规则计算置信度，整体置信度低于 0.5 时请用户补拍，补拍结果和之前的结果做幂等合并。 跨图片的冲突，比如两张图里同一个指标的值不同，两条都保留，只打 warning，交给下游处理。

二、多路召回与向量数据库索引优化

问题

问题分业务和技术两部分。业务上，用户的提问类型很杂，单一检索方式覆盖不全：

  • 精确指标：「糖化血红蛋白 6.4 偏高吗」，要查数值、参考区间和本人的历史数据；
  • 专有名词：「低密度脂蛋白参考区间」，要字面匹配；
  • 口语转述：「血糖有点高还能跑步吗」，要语义匹配。

另外还有两条约束：用户本人的指标数据不能进入共享索引；知识库要能按版本发布和回滚。 技术上，向量库里的数据量变大以后，索引本身的内存开销很大。

整体链路是：文本切块 → 查询计划（多 Query）→ 三路召回 → RRF 融合 → 精排。

文本切块

切块策略按数据形态选。每种算法放在单独的文件里，由注册表 resolve_text_strategy 选择，优先级依次是显式参数、环境变量 CHUNK_STRATEGY、自动选择。

  • evidence_row：用于指标目录、指南要点、病例这类结构化条目。一个条目转成一段自然语言，作为一个块。指标名、数值、单位和参考区间必须在同一个块里，拆开就没有意义了。
  • semantic_split：用于论文这类长文本。计算相邻句子的向量相似度，在相似度明显下降的地方切开，切分点落在主题之间，不会切断句子。
  • 父子块：用于只在开头出现一次主题的长文。比如一段讲血脂运动干预的指南，只有第一行写了「低密度脂蛋白胆固醇」，后面的块都不含这个词，检索时匹配不到，送去生成时还可能被对到错误的指标上。子块是带重叠的滑动窗口，父块是整篇文档，长度 1200 到 3000 字。检索用子块，命中后换成父块，再送去精排和生成。

没有 embedding 函数时，语义切分会退回滑动窗口。落库的策略标签这时记为 semantic_window，和实际行为保持一致，评测时口径才对得上。

在 30 项构造集、400 字符上限的条件下，固定长度切块的 Recall@5 是 0.833，按结构或语义切分都是 1.0。 上限改成 200 字符后，按符号切分的方案降到 0.867。父子块把证据中含主题词的比例从 37.5% 提高到 100%，单条证据的平均长度也从 130 字增加到 1,663 字。

查询计划

QueryPlanner 先把异常指标、用户提问和健康档案拆成若干主题，再为每个主题决定用哪些通道、查哪个分区、查询文本怎么改写。

查询数量有上限：每个主题最多三个通道，超出时按 SQL、BM25、Dense、Image 的优先级裁剪；所有主题的查询总数超过 15 个时，再按优先级裁剪一次。

改写方面，精确查询交给 BM25 和 SQL，语义扩写过的查询交给 Dense。同义词词典覆盖 30 个指标的口语叫法，比如「坏胆固醇」对应 LDL_C。 词典只在原查询后面追加标准术语，不替换原词：BM25 依赖原词做精确匹配，替换掉可能让原本命中的结果丢失。追加带来的额外召回交给后面的 RRF 和精排处理。

路由用规则而不用 LLM，是因为规则的结果可解释，没有调用成本，还能写单元测试。

三路召回

SQL 通道查两类数据：一类是指标目录中的参考区间，属于共享知识；另一类是用户本人的体检指标，可以附带生成时序趋势。 查用户数据必须带 user_id，user_id 为空时不返回任何用户数据。这个通道需要 metric_code 这样的结构化条件，只传自然语言查询会返回空结果。

BM25 通道用的是 Milvus 2.5 的 BM25 Function。说它是声明式全文检索，是因为 Function 在建集合时就写进了 schema： 写入时，服务端用 analyzer_params={"type": "chinese"}（jieba 分词）自动把文本转成稀疏向量；查询时直接传文本，服务端用同一个分词器切词并计算 BM25 分数。 客户端不需要稀疏编码器，稠密向量和稀疏向量存在同一个集合里。限制是 Function 只能在建集合时声明，之后要改 schema 只能删掉集合重建。 BM25 出错时会退回 LIKE 子串匹配，两个集合分别处理。

Dense 通道用 bge-m3 生成 1024 维向量，相似度用 COSINE。HyDE 只作用于这一路，默认关闭。

RRF 融合

rrf_score(d) = Σ_c  w_c / (K + rank_c(d))

融合只用排名、不用原始分数，因为三路分数的量纲不同：BM25 分数没有上限，Dense 是 0 到 1 之间的余弦相似度，SQL 没有分数。直接相加，结果会被尺度大的那一路主导。 RRF 只依赖排名，和分数尺度无关。某一路失败或返回空时，它不贡献分数，其余通道的排序不受影响。

网格搜索得出的最优 K 是 10，线上用的是 60。60 位于效果曲线平台区的中间，对数据分布不敏感；10 只是这批小样本上的最优值。 对结果影响更大的是每路的召回数量 N，最终定为 20。各通道权重默认相同，因为调权重需要足够的数据支撑，设得不当会对评测集过拟合。

同一路通道同时查知识库和论文库时，两个集合的分数同样不可比，所以用交错合并：两边各自的第 i 条结果分别放在第 2i−1 和第 2i 位。 直接首尾拼接的话，后拼进来的集合在 RRF 里的排名会系统性偏低。

在 9 条查询上，RRF 的 MRR 是 1.0，Dense 单路是 0.926，BM25 单路和直接混合分数都是 0.889。 在 92 条查询上，混合检索把 Hit@1 从 0.935 提高到 0.967，Recall@10 却从 0.692 降到 0.682：RRF 会把多路都排在前面的文档往上推，只出现在某一路里的长尾文档因此掉出了前十。

精排

精排用 bge-reranker-v2-m3。它是 Cross-Encoder，把查询和每个候选拼在一起打分，比双塔向量更准；但每个候选都要单独算一遍，也没法提前建索引，所以只能放在召回之后。

融合完成后先做父块扩展：子块换成父块文本，同一个父块只保留排名最高的子块。然后由 should_rerank 判断要不要精排： 查询不超过 12 个字、且原词已经出现在排名第一的候选里，说明粗排已经准确，跳过精排；语义类和意译类查询才进精排。精排调用失败时直接用 RRF 的排序。

在 6 条查询的基线测试里，精排后 Recall@10 从 0.526 降到 0.430，效果是负的。进入精排的候选为 20、50、100 条时，Recall@10 分别是 0.581、0.436、0.430，平均延迟分别是 881、975、1246 毫秒。 候选越多效果越差，说明问题出在精排环节：噪声候选把相关文档挤到了后面。这组实验用的是代理标签，样本量也小，结论只能作为方向参考。

按规模选择索引

文本数据分两个集合存放，稠密向量用不同的索引。evidence_text 存指南、病例和指标目录，数据量小，内存不是瓶颈，所以用 HNSW 优先保召回，参数 M=32、efConstruction=200、ef=128。 papers_lib 存论文全文，数据量大，HNSW 的图结构常驻内存开销太高，所以用 IVF_SQ8，nlist=512。两个集合都另有一个 BM25 稀疏向量字段，用 SPARSE_INVERTED_INDEX 索引。

HNSW 是分层的近邻图，查询时从顶层开始逐层向下贪心搜索。M 是每个节点的连边数，决定图的密度，影响召回上限和内存占用；ef 是搜索时候选队列的长度，用延迟换召回。 在 5,250 个向量、30 条查询上扫参数，以 FLAT 暴力检索的结果为真值：M 取 8、16、32 时，Recall@10 分别为 0.565、0.796、0.873，是影响最大的参数；ef 取 32、64、128 时，Recall@10 分别为 0.587、0.760、0.887。 最终参数下 Recall@10 为 0.977，P95 延迟 3.09ms。

IVF 先把向量聚成 nlist 个簇，查询时只搜距离最近的 nprobe 个簇。SQ8 把每一维从 float32 压到 int8，向量部分的内存约为原来的四分之一。 对比实验从 80 篇论文中取了 320 个真实段落向量，扩充到 2,560 个，nlist 设为 64，结果如下：

服务端预过滤和数据隔离

BM25 和 Dense 查询都把过滤条件写进 Milvus 的 expr，由服务端执行：

tenant_id == "..." and knowledge_version == "..." and source_type in [...] and chunk_role == "child"

过滤要在检索过程中完成。先取 TopK 再过滤的话，剩下的结果可能远少于 K 条，召回量会明显下降。

knowledge_version 保证只检索已发布的知识版本，草稿不会出现在线上结果里，知识库也能回滚。source_type 区分指南、病例和指标目录； 论文存在单独的集合里，由 _resolve_collections 负责路由。chunk_role == "child" 排除父块，因为父块和大多数查询都沾点边，参与召回会白占候选位。

用户的私有数据不靠向量层隔离。health_metrics 和 health_reports 不写入任何向量索引，只能通过带 user_id 的 SQL 通道读取。

所有索引都能从 PG 的 parsed_documents 全量重建，事实数据和索引分开存储。9 月 23 日，Milvus 内嵌 etcd 的数据目录没有挂到持久卷上，全部索引元数据丢失，最后就是靠这个设计恢复的。

目前的问题

  • tenant_id 读的是进程级环境变量，默认值 dev-tenant。系统实际上是单租户，schema 里只是预留了租户字段。
  • 论文库没有做全量向量化。300 篇原始论文中有 182 篇完成了正文解析，IVF 对比只用了上面的小样本。
  • _parallel_retrieve 名字叫并行，实际是串行的 for 循环，主题和通道数量增加时，延迟会线性增长。
  • agent 里 BM25 用的 top_k 是 10，和 RRF 实验定下的 N=20 不一致。

三、幻觉防范与记忆治理

无证据不说话。每条建议必须绑定证据 ID，然后过四类确定性校验：

  • 引用越过白名单即判伪造；
  • 数值与库内实测值比对，不一致就打回；
  • （另两类同属确定性规则，不依赖模型自评——因为自评在这里等于没有校验。）

记忆这一侧单独设了门禁，主要防的是投毒：

  • 检索到的文档永不入记忆——否则外部语料可以反向写进用户的长期记忆。
  • 置信度不足直接丢弃；要落库必须用户确认。
  • 存储用 AES-256-GCM 加密，content_hash 去重；注入时限定 token 预算，并在前端透明展示用了哪些记忆。
